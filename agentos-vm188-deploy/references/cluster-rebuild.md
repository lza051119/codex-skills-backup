# VM188 路线四：整个应用集群从零重建

## 适用条件与范围

用于具名 kind 应用集群本身需要重建，或用户明确要求重新搭建整套应用集群的任务。只是升级应用、数据库不用保留、个别 Pod 故障或 SSH 中断，不能自动推导为删除整个集群。

重建目标是 VM188 上的 kind 应用集群及其集群内网络、存储、身份与工作负载。宿主机操作系统、SSH 管理入口、独立的 k3s/Caddy、其 PVC 及其他环境继续保护；旧 k3s 业务环境仍保持退役。kind 内配套 Sandbox namespace 等要作为集群资源统一盘点，不能因为名字带 dev/test 就另行判断归属。

被重建集群内的数据不会自动保留。对用户需要保留的状态，先确认实际挂载位置及可用的导出/恢复方法；已明确允许丢弃的具名数据不增加历史搬运要求。路线选择和已有授权一起判断，不能用历史某次清库记录扩大本次删除范围。

## 桌面工具的覆盖要求

本文件补充路线定义和执行顺序，不表示已经提供跨版本一键重建器。历史复盘中的仓库 `make`、acceptance 或 reconcile 命令均不能作为当前执行入口。

先盘点桌面 `single-server-deploy/scripts/` 对本次目标的覆盖，并在 `records/<时间与 SHA>/` 记录已具备、需适配和需补齐的阶段。缺失的集群创建、网络/身份初始化或入口接线步骤，在桌面用原生 Git、Docker、kind、kubectl、OpenSSL、Caddy 等工具补齐并验证；不要在重建工具和必要输入尚未准备好时先删除旧集群。

## 执行顺序

1. 固定目标源码 SHA/tree、完整镜像与依赖清单，核对 kind 节点镜像、集群配置和容量。记录当前集群、节点容器、卷、kubeconfig、端口转发、入口上游与数据位置，形成精确的重建和保留清单。
2. 在容量允许时先准备制品与初始化材料，保留有效镜像和构建缓存。为需保留的数据准备可验证恢复输入；对获准丢弃的数据直接记录范围。明确失败后从哪个阶段续接，以及服务如何恢复。
3. 在固定 SSH 主机和运维锁下停止应用写入与自动扩容，按本任务的数据和活动任务要求完成停接。准确停止或调整指向旧集群的具名转发，保留 SSH 管理和独立 k3s 入口。
4. 只删除执行单中的 kind 应用集群及确认归属的资源；不用全局 Docker prune 代替范围核对。使用桌面独立配置与原生命令建立目标集群、必要的网络和 Sandbox 控制面，生成稳定位置的 kubeconfig，并核对新 context、节点和 API。
5. 按目标版本真实合同建立存储、角色、信任、身份和授权，导入完整目标制品。运行原生表结构初始化，配置真实 Provider/模型及凭据引用；顺序参考 [路线三](empty-redeploy.md) 的通用流程，具体 SQL 和初始化顺序重新核对目标代码，不能照搬 e082 的历史编号。
6. 恢复两个 BFF、Sandbox 模板/attestor、自动扩缩容、域名接线和 SSH 转发。集群重建可能改变地址及证书，按新实机状态更新确需调整的入口引用，保留独立 k3s/Caddy 的所有权和数据边界。
7. 核对主容器、初始化容器和模板的实际版本；完成登录、真实模型回复、文件上传/读取、Shell/Resource/Sandbox 与结果下载。需要恢复旧数据时另验证其身份和可读性，再同步桌面运行手册和阶段证据。

## 速度与失败处理

这条路线要重新建立的对象最多，通常慢于复用基础设施的路线。只有集群重建能解决的具体问题或用户选择足以支持这部分额外工作，不能把“从零”当作最稳定、最快或没有产品 bug 的保证。

阶段失败时先检查原生退出结果、已创建对象与数据状态，针对准确断点续接。重建后旧应用数据可能已不存在，不能把重新部署旧镜像称为完整回退；不得因半初始化而反复删建整个集群。
