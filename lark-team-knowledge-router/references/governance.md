# 团队知识治理基线

## 实时权威来源

公开分发版本不内置企业飞书 token。执行时按以下顺序定位治理来源：

1. 优先使用用户在当前请求中提供的知识库、文档或 Base 链接。
2. 没有链接时，按团队配置的标题搜索《团队知识库介绍与使用手册》、统一数据库使用指南和统一 Base。
3. 搜索出现多个候选时，让用户选择；不要根据相似标题猜测。
4. 找不到团队治理文档时，可以提供通用路由建议，但必须标注尚未经过团队实时规则验证。

资源标题、token、类型和父节点都必须实时解析；不得把示例名称或历史 token 当作当前事实。

## 六类知识空间

按资料的长期用途选择：

| 知识空间 | 主要内容 |
|---|---|
| 公共知识库 | 跨团队共用、长期稳定的权威资产；统一数据库位于此处 |
| POC 知识库 | POC 模板、过程资料、项目入口和 POC 使用导航 |
| 团队运营知识库 | 团队制度、会议、运营流程、报告和通用模板 |
| 测试知识库 | 测试规范、测试材料、验证经验和质量资产 |
| 产品知识库 | 产品基线、架构、需求决策、版本发布和产品资产 |
| 正式交付项目知识库 | 正式项目实施、运维、结项入口及交付规范 |

实际一级、二级目录必须从实时目录树读取，不要把本表当成完整目录清单。

## 目录权限

- 知识库负责人管理一级、二级目录结构。
- 其他负责人只维护自己所负责目录下的内容。
- 调整一级、二级目录前，向对应知识库负责人申请。
- 任何真人姓名在写入、发消息或设置权限前必须通过通讯录唯一核验。

## 数据库不变量

- 团队统一数据库本身是一个 Base 应用。
- Base 中的每张 table 才是数据表；form 必须依附于 table。
- 不能把一个 Base 应用“嵌套”进另一个 Base 应用。
- 多张关联表按业务文件夹组织，避免散落根目录。
- 其他知识库只保留业务入口，不维护第二份权威数据。
- 普通说明文档仍应按业务内容放在知识库目录；只有直接耦合的数据资产进入 Base 业务文件夹。

## 路由优先级

当一个对象看似适合多个位置时，依次判断：

1. 它的权威数据或正文应由谁长期维护？
2. 它服务的稳定业务对象是什么？
3. 用户通常会在哪个工作场景寻找它？
4. 是否已经存在同类目录或权威原稿？

先确定唯一原稿，再列出所有入口。不要用“多复制几份”解决多场景访问。
