# POC 管理表案例

## 来源

案例整理自团队内部关于 POC 数据治理的讨论，只保留可复用的知识治理结论，不包含聊天原文、个人标识或无关信息。

## 争议

讨论中提出：晴天纪数据库中的 POC 表已经链接各 POC 知识库主页；如果 POC 知识库里的表格又链接回晴天纪数据库，看起来像“索引回去”，是否重复管理？

## 结论

不是重复管理，而是两个不同方向的导航：

- 晴天纪数据库 → POC 知识主页：回答“这条数据属于哪个项目，项目背景在哪里”。
- POC 知识库 → 晴天纪数据库表或表单：回答“在这个项目里去哪里填数据、查看数据”。

只要两处都指向同一份数据源，就仍然是一份权威原稿。

## 正确执行

1. 先在晴天纪数据库中找到或建立 POC 管理数据表。
2. 如果需要信息收集，在该数据表下创建表单。
3. 若某个 POC 有多张关联表，在统一 Base 中建立业务文件夹组织整组表。
4. 在 `POC 知识库 / 使用说明` 和具体 POC 项目目录建立入口，可使用快捷方式、引用链接、嵌入权威视图或表单链接。
5. 入口只负责导航，不复制数据。

## 错误执行

- 在 POC 知识库重新创建第二份多维表格并长期维护。
- 把整个旧 Base 应用当作一个文件放进晴天纪数据库。
- 只迁移关联表中的一张，导致 Lookup、公式或自动化断裂。
- 把入口放在 POC 知识库根目录，而不是 `使用说明` 或具体项目节点。

## 对 Codex 的测试提示

用户说“帮我建一个 POC 需求表单”时，Skill 应先回答并执行两阶段方案：

```text
权威原稿：晴天纪数据库 / <POC 业务位置> / <承载数据表>
表单：依附于上述数据表
业务入口：POC 知识库 / <具体一级目录> / <具体二级目录或项目页>
验证：所有入口指向同一表；未在 POC 知识库复制第二份数据
```

如果实时目录中不存在合适位置，先找知识库负责人确认，不直接创建新的一级、二级目录。
