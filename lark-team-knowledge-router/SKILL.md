# 飞书团队知识归档

把“文件放哪、表单建哪、入口放哪”变成一个可执行流程。核心不变量是：先确定唯一权威原稿，再把入口放进实际业务目录；任何写入都以飞书实时目录和权限为准。

## 依赖预检

在读取飞书实时数据前检查当前环境是否具备 `lark-cli`，以及本次任务需要的飞书插件或 `lark-*` 技能。

- 能力齐全：直接继续，不额外打扰用户。
- 缺少能力：明确列出缺失的能力，并询问“当前缺少对应的飞书插件或技能，是否要安装或启用后继续？”
- 用户同意：使用当前平台提供的官方安装机制；不要猜测不存在的插件名称、下载地址或插件 ID。
- 用户拒绝或暂时不能安装：可以根据治理规则提供建议，但必须标注“未连接飞书实时状态，尚未验证目录、权限和 token”，不得执行或声称已完成飞书写入。

只提醒和询问，不静默安装插件，不因为缺少一个无关能力而阻塞其他已具备能力的操作。

## 需要配合的技能

按实际资源类型调用以下技能，并在第一次操作前完整阅读对应 `SKILL.md`：

- `lark-contact`：核验人名。
- `lark-wiki`：读取知识空间、目录和节点，创建或移动节点、快捷方式。
- `lark-drive`：读取文件元数据，移动普通云空间文件。
- `lark-doc`：读取或编辑文档内容。
- `lark-base`：读取和操作多维表格、数据表、文件夹、视图与表单。
- `lark-shared`：处理身份、授权和缺失权限。

## 运行时参考

- 每次触发都阅读 [references/governance.md](references/governance.md)。
- 判断归属、移动文件或建设入口时阅读 [references/routing-matrix.md](references/routing-matrix.md)。
- 执行任何写入或迁移前阅读 [references/execution-checklists.md](references/execution-checklists.md)。
- 涉及 POC 表单或用户质疑“双向链接是否重复”时，再阅读 [references/poc-form-case.md](references/poc-form-case.md)。
- 需要向团队成员说明如何提需求时阅读 [references/team-usage-examples.md](references/team-usage-examples.md)。

## 固定规则

始终遵守以下规则：

1. 一份权威数据源，多处业务入口。
2. 晴天纪数据库是统一 Base 应用；表单依附于具体数据表，不是独立文件。
3. 迁移单位是单张表或相互依赖的一组表，不是把一个 Base 应用嵌进另一个 Base 应用。
4. 同一业务有多张关联表时，在统一 Base 中使用同一业务文件夹组织，保留关联、公式、Lookup、视图和自动化。
5. 文件、数据入口和快捷方式必须放在准确的一级、二级目录或具体项目节点下，不得直接丢在知识库根目录。
6. 一级、二级目录结构只有知识库负责人可以调整；目录缺失或归属有歧义时先确认，不得擅自新造结构。
7. 每次写入前读取实时目录树和目标资源元数据。参考文档中的 token 只作定位提示，不替代实时解析。
8. 用户提到任何真人姓名时，先用通讯录按姓名搜索。零匹配或多匹配时停止涉及该人的消息、权限、负责人和文档写入。
9. 写入前搜索目标位置是否已有同一原稿、同名节点、同名表、同名表单或相同目标的快捷方式；能够复用或更新时不得重复创建。
10. “目录下面”必须落实为目标节点的真实 parent；不能只把标题写得像目录，也不能把节点创建成根目录的同级项。

## 工作流

### 1. 明确用户授权范围

区分三档授权：

- **建议模式**：“这个文件放哪、帮我判断”。只做只读检查、路由卡和执行建议。
- **执行模式**：“直接归档、迁移、建立、放进去”。可执行明确范围内的创建、移动、更新和入口建设。
- **破坏性模式**：删除、覆盖、停用原稿、批量改权限或调整一级/二级目录。必须取得针对准确对象的单独授权。

不要把分类请求扩大为移动，也不要把移动请求扩大为删除旧数据。源表的停用或删除必须单独确认。

### 2. 解析对象与责任人

先取得真实 URL/token、文件类型、标题、当前父节点、创建人/负责人和可用权限。

- 有人名：先走 `lark-contact` 唯一解析。
- 有 `/wiki/`：先走 `lark-wiki` 解析节点和真实对象。
- 有 `/base/`、bitable 或多维表格：先走 `lark-base +url-resolve` 或标题解析，再读取 Base block。
- 普通云文件：走 `lark-drive` 元数据。
- 文档内嵌 Base：先用 `lark-doc` 提取 token，再切到 `lark-base`。

### 3. 读取实时治理信息

至少完成以下只读检查：

1. 读取《团队知识库介绍与使用手册》中与目标类型相关的章节。
2. 读取目标知识空间的当前目录树，定位到具体一级、二级目录或项目页。
3. 数据表/表单任务同时读取《晴天纪数据库使用指南》和晴天纪数据库当前 block 树。
4. 对既有 Base 迁移，盘点全部表、文件夹、关联、公式、Lookup、视图、自动化和权限。
5. 搜索目标目录和统一数据库，确认是否已经存在可复用的权威原稿或入口。

### 4. 生成路由卡

在写入前形成一张简短路由卡：

```text
对象：<标题与类型>
业务域：<公共/POC/团队运营/测试/产品/正式交付>
现有原稿：<无/路径与链接/同名冲突>
权威原稿：<知识库 / 一级目录 / 二级目录 / 节点>
业务入口：<一个或多个准确目录>
负责人：<通讯录已核验的人>
执行动作：<创建/移动/引用/快捷方式/不处理>
幂等判断：<新建/复用/更新/跳过>
验证项：<可访问性、唯一原稿、关联关系、入口位置>
```

如果无法给出完整路径，不得开始写入。

### 5A. 普通文件归档

1. 依据内容的长期用途选知识库，而不是根据临时发送群或当前所在位置判断。
2. 在实时目录树中选择准确目录节点。
3. 搜索目标目录：同一原稿已在正确位置时跳过移动；入口已存在且指向正确时跳过创建。
4. 优先移动原节点，避免复制出第二份权威文件；确需副本时明确标注副本用途。
5. 如果业务在其他知识库也需要访问，创建快捷入口而不是复制正文。
6. 移动后复读目标节点，确认标题、真实父节点、权限和链接。

### 5B. 数据表或表单建设

严格分两阶段执行。

第一阶段，建立权威数据源：

1. 在晴天纪数据库中定位现有业务文件夹，必要时提出新文件夹方案。
2. 搜索同名或同用途的表、表单和文件夹，先判断复用、更新还是新建。
3. 若用户说“建表单”，先确认承载数据的表。没有表时先建表和字段，再在该表下建表单。
4. 若同一业务有主表、明细表、配置表等，把它们作为一组放入同一文件夹。
5. 配置或迁移后检查字段、关联、公式、Lookup、视图、自动化、权限和负责人。

第二阶段，建设业务入口：

1. 列出所有实际使用场景。
2. 在每个业务知识库的准确目录放置快捷方式、引用链接、嵌入视图或表单访问链接。
3. 入口旁写明权威原稿、用途、负责人和适用范围。
4. 验证不同入口都落到同一份数据源。

### 6. 迁移既有 Base

禁止把整个旧 Base 作为一个文件塞入晴天纪数据库。正确做法是：

1. 盘点旧 Base 的全部表和依赖。
2. 在晴天纪数据库建立或选择业务文件夹。
3. 按依赖顺序迁移主数据表和业务表。
4. 重建并核对关联、公式、Lookup、自动化和视图。
5. 在原知识库准确位置建立指向新原稿的入口。
6. 对每张表记录“未开始/已复制/已核对/已切换入口/可停用”状态；不得用整体成功掩盖部分失败。
7. 验证稳定前保留源表；停用或删除另行确认。

### 7. 验证并汇报

完成后必须重新读取并报告：

- 权威原稿的实际路径和链接。
- 每个业务入口的实际路径和链接。
- 是否仍存在第二份原稿。
- 表间关联、公式、Lookup、自动化、视图和权限是否保持。
- 哪些事项因为目录权限、缺失负责人或高风险删除而未执行。

如果验证失败，不得声称完成；保留源数据并报告准确阻塞点。

部分失败时必须列出已经完成和尚未完成的对象，保持旧入口和源数据可用。不要自动回滚已验证成功的独立对象，也不要继续执行依赖于失败对象的后续步骤。

## 输出要求

建议模式输出路由卡和待确认事项。执行模式完成后输出：

1. 实际权威原稿路径与链接。
2. 已建立或复用的全部业务入口。
3. 通讯录核验、权限核验和幂等判断结果。
4. 数据表、表单、关联、公式、Lookup、视图和自动化的适用检查结果。
5. 未执行、部分失败或仍需负责人批准的事项。

不要在输出中暴露 access token、app secret、授权码或其他凭据。

## 常见拒绝条件

- 目标只有知识库名称，没有具体目录。
- 人名无法在通讯录唯一匹配。
- 用户要求“建表单”但没有承载表，且业务字段无法从上下文确定。
- 迁移会破坏跨表关联、自动化或权限，且没有可验证的恢复方案。
- 需要调整一级、二级目录但没有知识库负责人批准。
- 操作会删除、覆盖或停用源数据，而用户只授权了归档或迁移。

遇到这些情况时，先完成所有安全的只读检查，再用最少问题向用户补齐信息。
