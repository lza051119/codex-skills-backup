# 测试与开发 SKILL

来源：[飞书《测试与开发 SKILL》](https://xcnvtd6v6w7y.feishu.cn/wiki/RVqXwqLjPiVEGSkVXHWcyxiTnde)，同步版本：revision 522。正文保留来源流程，飞书资源引用转换为可点击链接。

如果你有测试或修复相关的任务，例如用户给出的功能范围、用户在使用中发现的问题、缺陷定位或修复验证，你必须作为精通测试与开发的资深工程师，基于证据精确定位问题，逐步排查根因，并完成修复。

总体按照“白 → 黑 → 白 → 判定 → 开发 → 报告”推进。

## 第一阶段：静态代码分析与测试用例设计

用户提出的要求往往比较模糊，必须先通过静态阅读文档与代码解析用户意图，把模糊的要求细化为明确的测试对象与测试点，再设计测试用例。

先阅读与任务直接相关的产品与决策文档、架构文档、接口契约、核心数据结构、代码和已有测试，形成测试依据（test basis），建立以下对照：

- 目标要求是什么；
- 当前代码实际实现了什么；
- 相关入口、调用链、状态转换和错误处理在哪里；
- 已有测试覆盖了什么，缺少什么；
- 该行为是否已经冻结，是否属于当前交付范围。

基于测试依据识别测试条件，并根据任务风险和影响范围设计必要的测试用例，既包括代码级测试，也包括从用户视角出发、覆盖真实用户旅程的测试。用例应明确前置条件、操作或输入、预期结果和判定依据。

## 第二阶段：端到端黑盒测试

凡任务涉及 Web 页面、用户登录、管理后台或浏览器可访问的真实用户旅程，必须使用 [agent-browser skill](https://github.com/vercel-labs/agent-browser) 进行端到端的黑盒测试，若 agent browser 未安装，则请先下载并配置 skill、cli 到对应 coding agent harness。

测试必须从真实用户入口开始，执行实际交互，并记录足以复核结论的页面状态、请求与响应、错误信息、权限差异、重复执行结果以及必要的截图。需要时使用不同账号、独立会话或不同输入进行对照。

如果任务没有浏览器可访问的测试面，才可以说明 `agent-browser` 不适用，并选择与任务匹配的其他验证方式。

## 第三阶段：白盒动态诊断

如果环境和权限允许，继续使用只读运行时证据定位根因（日志、数据库等），将黑盒现象对应到具体服务、模块、配置、数据状态、调用链或部署状态。

如果关键环境不可达、权限不足、日志缺失或证据相互矛盾，必须明确说明限制，不得通过推测补齐根因，也不得把未验证的结果写成通过或已定位根因。

不得在测试或诊断过程中擅自修改线上数据、配置、部署状态或其他外部系统状态。

## 第四阶段：判定

基于前三阶段的测试结果和证据，每个问题只能归入最符合证据的一类：

- 可交付：目标已实现，黑盒测试通过；
- 代码缺陷：已冻结目标存在，代码行为与目标或契约不一致；
- 部署缺陷：代码目标正确，但环境、配置、制品、路由、迁移或运行状态错误；
- 已规划且阻塞：目标已冻结但尚未实现，并阻塞用户旅程；
- 已规划且不阻塞：目标已冻结但尚未实现，但当前旅程仍可完成；
- 范围外或未冻结：没有足够产品依据，不作为缺陷；
- 证据不足：无法完成必要验证，不判定为通过或失败。

“未实现”只有在文档确认属于当前目标时，才可以归为“已规划且阻塞”或“已规划且不阻塞”；不能直接报为 bug。

只有判定为代码缺陷且属于任务范围的问题进入第五阶段开发；其余类别不进入开发，在报告中说明即可。

## 第五阶段：开发

必须从根本上解决问题，优雅的重构好于丑陋的补丁，鼓励小范围重构以提升代码质量。注意文档与代码的同步，注意清理过度防御与冗余死代码。修复代码必须合并到相关分支才算完成，未合并不得进入第六阶段写报告。

## 第六阶段：报告

任务结束时交付一份人类友好、可复核的 Markdown 测试报告。报告是一个文件夹，命名格式为 `report-YYYYMMDD-<任务主题>`，内部结构如下：

```
report-20260904-登录失败排查/
├── report.md        # 唯一的 Markdown 报告
├── images/          # 全部截图，按文中引用顺序编号命名
│   ├── 01-登录页-初始状态.png
│   ├── 02-提交后-报错弹窗.png
│   └── 03-修复后-登录成功.png
└── attachments/     # 可选：日志、HAR 等非图片证据
```

`report.md` 依次记录：任务目标与来源；测试依据、范围、环境、候选版本和执行时间；实际执行的测试用例或场景，以及关键用例的前置条件、预期结果、实际结果和测试状态；黑盒证据、静态分析、动态诊断和根因；结论汇总与后续动作；修复内容与变更说明；未执行、阻塞或不适用的测试及原因。

黑盒测试的每个操作步骤（每次点击、输入、提交）都必须截图，存入 `images/` 并按引用顺序编号；日志、HAR 等非图片证据放入 `attachments/`。报告不复制全部测试脚本或用例库，但必须说明实际执行了哪些测试、结果如何、哪些范围没有覆盖。

测试报告不要提交到代码仓库。
